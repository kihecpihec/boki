## Implementation Sequence

### 1. Define Deterministic Run and Route State

Create small readable state types under `Game/Assets/Scripts/Core/` and `Game/Assets/Scripts/Routes/`. Separate pure rules from MonoBehaviour wiring, using assembly definitions only where needed for EditMode tests, following the existing combat rules/test setup.

- Represent level identity, A/B/C choices, and an unchosen value explicitly. Reject invalid identities and out-of-order choices without modifying state.
- Initialize run state from [Gameplay §4](../Gameplay.md#4-game-state-and-saving-rules): HP, battery, XP, upgrades, route choices, kill count, start time, and a copied unlock snapshot.
- `New Run` resets the existing state and copies the supplied unlock values. Neither later mutation of the source nor a scene load may change that snapshot.
- Keep unlock input in memory for M3. Leave a direct integration point for M5 to supply saved flags at new-run initialization; no save framework or PlayerPrefs implementation is required now.
- Do not grant placeholder rewards or increment progression fields merely to exercise them. Test reset behavior directly through the state API.

### 2. Implement Route Availability and Selection

Create `RouteManager` and a deterministic rules helper under `Game/Assets/Scripts/Routes/`.

- Evaluate connections exclusively from the canonical [route matrix](../Gameplay.md#3-allowed-route-matrix) and the current run's unlock snapshot.
- Before selection, check `ROUTE_LOCK` before `PERSISTENT_LOCK`, then return `AVAILABLE`. Forest A/B start available; Forest C requires its snapshot flag. City/FERI require their preceding choice.
- Accept a choice only for the active level and an available gate. Store it immediately before notifying views or allowing a transition.
- Once chosen, return `SELECTED` for that gate and keep all alternatives closed as route locks. Re-entering the selected gate must not select again or emit another selection notification.
- Reject stale triggers, locked choices, repeated requests, and choices for another level. Preserve all earlier choices when advancing.
- Keep availability queries free of state changes. Reopening a scene or refreshing UI must not reopen alternatives.

### 3. Add the Persistent Runtime Session

Create `Game/Assets/Scripts/Core/RunSession.cs` as the single runtime owner of run state, following [Architecture §4.2](../Architecture.md#42-runsession-reset-on-death--new-run).

- Retain one active instance across scene loads using a simple bootstrap or `DontDestroyOnLoad`; discard duplicates before they reset or bind state.
- Support launching the owned Forest test scene directly. Initialize a new run once; loading City must continue it rather than reset it.
- Keep scene objects, cameras, UI, enemies, and event subscriptions scene-local. Rebind them to the surviving session after a load and unsubscribe on disable/destruction.
- Make new-run initialization explicit. Retry resets the existing session and loads the Forest entry scene, including when death occurs in City.
- Validate scene destinations before committing to a load. Guard transition/retry requests so overlapping triggers or repeated button clicks cannot issue duplicate loads.
- If City is opened directly without a preceding Forest choice, report the missing prerequisite clearly and provide a way to start at Forest; do not fabricate a route choice or show valid City exits.

### 4. Connect M2 Health, Death, and Retry

`PlayerHealth` currently owns a scene-local `HealthState`; `CombatSession` currently reloads its own scene. Adapt code without breaking the standalone M2 scene.

- Let a session-bound `PlayerHealth` use the session-owned health state as its single HP authority. Retain scene-local health for the existing M2 setup; avoid two writable HP values synchronized through events.
- Carry remaining HP into City without restoring it during `Awake`, `OnEnable`, or component rebinding. Make subscription order safe so initialization cannot miss a death notification or duplicate listeners.
- Keep UI and shutdown behavior scene-local. Reuse or minimally adapt `CombatSession`/`CombatView`, or introduce a small M3 adapter if that preserves the M2 flow more clearly.
- On death, stop movement, camera input, laser, and scene enemies; show `ABSENT` and release the cursor as in M2. Dead players cannot select gates or advance levels.
- M3 Retry starts a new run at Forest with reset state, HP, spawn, enemies, camera, and cooldowns. The standalone M2 Retry must still reload `Combat_Test.unity` correctly.

### 5. Wire Gates and the Demonstration Transition

Create `RouteGate` with explicit references to its level/route identity, a blocking collider, a separate selection trigger, and a minimal readable sign or view.

- Apply the canonical gate states and exact lock messages from [Gameplay §4](../Gameplay.md#4-game-state-and-saving-rules). Locked gates physically block the player and disable their selection trigger; their message remains visible without requiring entry into that disabled trigger.
- Available gates are passable and selectable. Selected gates stay passable; alternatives close immediately. Accept only the active player, including correct identification when a child collider enters.
- Account for the player's `CharacterController` when configuring trigger detection. Verify actual crossings in Play Mode rather than assuming trigger callbacks occur with the chosen physics setup.
- Place selection triggers far enough beyond the entrance that closing alternatives does not trap or intersect the player. Use primitive colliders and restrained visuals.
- Add a minimal Forest exit after the branches rejoin. Require a Forest choice, preserve the session, and load City once. This M3 test transition does not earn or save an unlock; M5 adds milestone persistence.
- End the City demonstration at a clearly marked test endpoint after a valid City selection. Do not imply the full FERI level or boss exists; verify FERI rules in EditMode until M4 integration.

### 6. Assemble and Import in Unity

After ownership is confirmed, create the two test scenes in the pinned Editor. Use short primitive A/B lanes and blocked C gates, a shared start and exit, one camera/listener, one main light, and a few melee instances to verify carried damage and death. Avoid a spawning system or navigation work.

Required Inspector assignments:

- Session/bootstrap: Forest entry destination and consistent runtime initialization policy.
- Scene coordinator: session binding, player health/movement/laser, follow camera, melee instances, HP view, death panel, and Retry button.
- Route manager: current level and session; gate views subscribe to its state changes.
- Each gate: unique route identity for that level, primitive blocker, separate selection trigger, player filter, and sign/view.
- Forest exit: session, current level/choice check, and City destination. Put the exit beyond the route selection area.
- Player/camera/enemies: preserve M1/M2 assignments and collision masks. The existing player and enemies use `Ignore Raycast`; gate blockers must still obstruct movement and behave consistently with camera and weapon environment filters.
- UI/build: one Input System EventSystem; readable signs and HP at 1280×720. Include both scenes explicitly in any M3 player build.

Import externally created scripts/assets through Unity **6000.6.7f1**, letting Unity generate `.meta` files. Preserve existing GUIDs. If the Editor cannot run, report pending imports and missing metadata; do not describe the assets as ready to integrate.

## Verification and Completion

Add EditMode tests for behavior and edge cases:

- Every connection in the canonical matrix, including forbidden connections with all C flags enabled.
- All eight unlock snapshots across reachable route histories: at least one allowed continuation, with intentional first-run forced choices preserved.
- Forest C gating, missing predecessor choices, invalid identities, and out-of-order selection rejection.
- `ROUTE_LOCK` priority when both locks apply, plus allowed-but-persistently-locked C gates.
- Immediate selection, selected-gate stability, closed alternatives, repeated/competing requests, and exactly one selection notification.
- Snapshot isolation: changing the source flags during a run does not open gates; a subsequent new run receives the updated values. Disk saving and earned milestone tests remain M5.
- New-run defaults and reset of modified run fields, including all route choices; scene advance preserves choices and damaged HP.
- Session-bound health uses one authority and retains existing health/death semantics. Keep the M2 health tests passing.
