## Implementation Sequence

### 1. Confirm Movement Decisions

The canonical documents specify the controls and arcade controller, but do not define the steering model or boost tuning. Resolve these before implementing the affected behavior:

- Does WASD move relative to the camera, or does W/S control forward/reverse while A/D steers the scooter?
- What are the boost duration, speed increase, cooldown, and airborne behavior?
- What baseline speed, turning response, jump height, and air control should the first prototype use?

Keep tuning values serialized in the Inspector. Record agreed gameplay behavior and initial values in the canonical [Gameplay document](../Gameplay.md#0-gameplay-pillars-and-controls), rather than making this plan a second rules source. These decisions do not block creating the arena or basic camera follow.

### 2. Wire Input

- Reuse `Game/Assets/InputSystem_Actions.inputactions` and its `Player/Move`, `Player/Look`, and `Player/Jump` actions.
- The template has a `Sprint` action. Rename it to `Boost` through the Input Actions editor and preserve its action identity and unrelated bindings. Verify the Left Shift binding and update any references together.
- Use serialized input action references in the controller and camera; avoid a new input framework or legacy `Input.GetAxis` calls.
- Enable and disable owned actions with component lifetime. Clear held movement and transient input when disabled so reopening Play Mode or regaining focus cannot leave movement stuck.
- Limit M1 acceptance to keyboard and mouse; retain unrelated template actions and bindings.

### 3. Implement Scooter Movement

Create `Game/Assets/Scripts/Player/ScooterController.cs`:

- Read movement and apply the agreed steering model. Clamp input magnitude so diagonal input cannot exceed the intended speed.
- Move through `CharacterController.Move`; apply gravity explicitly and use elapsed time for movement and timers.
- Support grounded jumping, stable landing, and head collisions without repeated jumps from a held key.
- Implement a short boost using the agreed duration and recovery rules. Prevent held input from unintentionally becoming permanent boosted movement.
- Expose movement, jump, boost, and turning settings with readable Inspector labels. Keep temporary state inside the component.
- Use the controller capsule for collision; do not add a competing Rigidbody movement system. Any cosmetic model rotation belongs on a visual child.

### 4. Implement the Camera

Create `Game/Assets/Scripts/Player/ThirdPersonCamera.cs`:

- Follow an assigned player pivot in `LateUpdate` and orbit using mouse input.
- Expose sensitivity, follow distance, pivot height, and vertical angle limits. Keep the view upright and prevent orbit flips.
- Treat mouse delta as pointer displacement; avoid applying frame-time scaling that makes sensitivity depend on frame rate.
- Use a simple sphere cast between the pivot and desired camera position to shorten the follow distance near obstacles. Ignore the player and trigger colliders; restore distance smoothly when clear.
- Lock the cursor during active play. Provide cursor release and recapture for testing, and stop look input while released or unfocused. This is not the later pause system.
- Validate required references and avoid repeated errors when a reference is missing.

### 5. Assemble the Player and Arena in Unity

Create the following assets in the pinned Editor:

- `Game/Assets/Prefabs/Player/Boki_Player.prefab`: root `CharacterController` and `ScooterController`, primitive visual child indicating forward direction, and a camera pivot child. Keep placeholder visual colliders disabled or removed.
- `Game/Assets/Scenes/Gameplay_Test.unity`: player instance, camera with `ThirdPersonCamera`, flat floor, boundary walls, ramp, low jump obstacle, overhead obstacle, and a wall/corner for camera checks.

Use primitive colliders, simple materials, one main light, and existing URP settings. Keep the arena enclosed so it needs no out-of-bounds or death system for M1.

Required Inspector assignments:

- Controller: `CharacterController`, movement/jump/boost action references, movement orientation reference if required by the agreed model, and tuning values.
- Camera: follow pivot, look action reference, camera distance and angle settings, and an environment collision mask excluding player geometry.
- Scene: spawn above the floor with clearance, controller capsule matching the placeholder, and exactly one active gameplay camera and Audio Listener.

Import externally created scripts in Unity **6000.6.7f1** and let Unity generate their `.meta` files. Preserve all existing GUIDs. If the Editor cannot run, report pending import and missing `.meta` files explicitly; the assets are not ready to integrate until imported and checked.
