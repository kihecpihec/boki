# M5 Handoff and Verification

Implemented on `feat/m5-persistent-unlocks`. The developer authorized updates to all three M4 level scenes. The developer subsequently authorized committing, pushing, and merging the milestone into `dev`.

## Delivered Behavior

`PersistentUnlocks` keeps permanent progress separate from `RunState`. The PlayerPrefs adapter uses `boki.unlock.forestC`, `boki.unlock.cityC`, and `boki.unlock.feriC`. Missing keys and values other than `1` remain locked. Only the earned key is written; `PlayerPrefs.Save()` runs immediately. Already earned milestones do not repeat writes/saves or clear other flags.

Sessions whose existing Forest entry destination is `Level1_Pohorje` automatically use permanent saving. There is no Inspector checkbox to enable. This also supports an M4 scene already open in the Editor when M5 scripts arrive. Forest and City exits save after prerequisites/destination validation and before advancing/loading. The existing classroom trigger is the arena-entry milestone for FERI C; it requires a living player and a selected FERI route. Arena entry is accepted once per run. It does not start a boss or announce victory.

Session initialization, Retry, and Start New Run read saved flags into a value snapshot. Earning flags never modifies that snapshot. The canonical route matrix still applies after every unlock. Standalone M3 scenes retain their in-memory behavior.

The three scenes retain their GUIDs and existing A/B content. C now has a passable floor, a primitive tunnel roof and side columns, and an exit marker. Forest also has overhead rave-tunnel beams. All lanes use the existing gates, route dividers, rear seals, and encounter roots. C roots are empty in this graybox; pickups, lighting/glitch behavior, Guilt events, traps, the functional `POWER OFF` panel, and boss modifiers remain later work.

## Fix for Unlocks Never Opening After New Run

The initial M5 implementation depended on a newly serialized `persistUnlocks` checkbox. A production scene already open before the update could retain the default `false` value. Its surviving session then skipped every milestone write and continued reading the all-false in-memory flags on Retry/New Run. Loading later scenes did not replace that session. The original automated checks reopened freshly updated assets and missed this cached-scene case.

A regression probe forced the old unchecked value before Play Mode. Before the fix it reproduced `Forest exit saves immediately` failing after the real Forest-to-City transition (`/tmp/boki-m5-stale-before.log`, exit 1). The checkbox has now been removed: the existing Pohorje entry destination determines production saving. Existing M3 test destinations continue to use their separate in-memory behavior. The obsolete checkbox data was removed from the three production scenes without changing other scene content.

After the fix, the same scene smoke suite passed all eight histories (`/tmp/boki-m5-stale-after.log`). All 32 EditMode tests passed again (`/tmp/boki-m5-fix-editmode.xml`); the M3 scene/UI/death/Retry regression passed (`/tmp/boki-m5-fix-m3.log`), and the Linux development player rebuilt (`/tmp/boki-m5-fix-build.log`). Metadata, scene references/GUIDs, ownership, documentation links, and whitespace checks also passed.

Earlier attempts made with saving disabled did not write permanent flags. The fix does not fabricate missing progress; earn the milestones again through normal play. Exit Play Mode and start from Pohorje after compilation finishes. No Inspector toggle is required, including for an already-open M4 scene.
